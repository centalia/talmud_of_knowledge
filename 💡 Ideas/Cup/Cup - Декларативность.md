> [!abstract] Статус: В планах
> Декларативный подход к управлению пакетами и настройками системы. Вдохновлено философией NixOS.
## 💡 Суть
Обычно мы управляем системой **императивно**: пишем команды (`cup install firefox`, `cup install git`), и система меняет свое состояние шаг за шагом. 
**Декларативный** подход означает, что мы описываем **желаемое состояние** (что должно быть установлено), а программа сама приводит систему к этому состоянию.
###  Императивный vs Декларативный подход
**Сейчас (Императивно):**

```bash
cup install firefox
cup install thunar
cup install neovim
```
**Будущее (Декларативно):**  

Создаем файл `~/.cup/packages.txt` (или `manifest.yaml`):

``` text
firefox
thunar
neovim
```

И запускаем одну команду: `cup sync`.

## 📜 Три столпа (взято из Ansible)
### 1. Идемпотентность (Idempotency)
Это значит, что повторный запуск команды не меняет систему, если она уже в нужном состоянии.
*   **В cup:** Если пакет из манифеста уже установлен (и записан в нашу БД или есть в `pacman -Q`), `cup sync` **пропускает** его. Никаких переустановок. Если конфиг уже на месте — он не перезаписывается.
*   *Как проверить:* Запустил `cup sync` два раза подряд. Второй раз должен отработать моментально и сказать: "Everything is up to date".
### 2. Единый манифест (Unified Manifest)
Вместо кучи разрозненных команд мы используем один файл конфигурации (например, `~/.cup/manifest.yaml` или `.toml`).
*   **В cup:** Этот файл содержит список всего, что нужно установить: пакеты из `pacman`, пакеты из `yay` (AUR) и вызовы наших модулей (например, `yamusic`).
*   *Пример структуры манифеста:*
``` YAML
packages:
      pacman: [firefox, thunar, neovim]
      aur: [visual-studio-code-bin, pycharm]
      modules: [yamusic]
```
### 3. Роли (Roles / Profiles)

Разделение софта на группы в зависимости от того, для чего используется машина.
- **В cup:** Мы создаем разные манифесты (или секции в одном манифесте) под разные задачи: `desktop.txt`, `server.txt`, `dev.txt`.
- _Как работает:_ Пользователь пишет `cup sync --role desktop`. Скрипт читает только пакеты для десктопа и ставит их. Если он на сервере — пишет `cup sync --role server` (и ставит `nginx`, `docker`, но не ставит графические оболочки).
- _Связь с Bootstrap:_ Роль `desktop` может автоматически вызывать скрипт настройки KDE.
  
###  Как должна работать команда `cup sync`

1. Прочитать манифест (YAML/TOML/TXT).
2. Понять, какие роли активны (или взять все).
3. Сравнить список из файла с тем, что уже установлено (и записано в локальную БД `~/.cup/db.sqlite3`).
4. Если пакет в файле есть, а в системе нет — **установить** его.
5. Если пакет есть в системе, но его удалили из файла — **предложить удалить** (опционально).
6. Если пакет установлен, но версия устарела — **обновить**.
7. Вывести итоговый отчет: `Installed: 3, Skipped: 5, Failed: 0`.

## 🎯 Профиты

1. **Воспроизводимость.** Переустановил систему (или купил новый ноут) -> склонировал свой dotfiles-репозиторий -> запустил `cup sync` -> получил точно такой же набор софта, как было.
2. **Версионирование.** Файл `packages.txt` можно хранить в Git. Ты всегда видишь, когда и какой софт добавил.
3. Не нужно вспоминать, какие пакеты ты ставил. Всё записано в файле.
4. **Связка с Bootstrap:** Скрипт `Cup - Bootstrap` будет использовать этот файл для развертывания KDE и остального окружения.

## ⚠️ Риски и сложности

- **Разные источники:** Как в одном файле указать, что `firefox` — из `pacman`, а `yamusic` — из `modules`? Нужен формат (например, `aur:yay`, `module:yamusic`).
- **Конфликты:** Что делать, если пакет зависит от другого пакета, которого нет в списке? (Пока доверить это `pacman`).
- **Удаление:** Сложно понять, что пакет был удален намеренно, а не сломался. Возможно, `sync` должен только добавлять, но не удалять.
