## ## 💡 Суть

Flatpak-версия MAX (`ru.max.MAX`) со времнем перестает запускаться. 

Запуск через терминал `ru.max.MAX` показал:
```
[11-11-2026 14:41:03.677] [Warning] Qt: Session management error: Could not open network socket (:0)
[11-11-2026 14:41:03.679] [Error] [NetworkChangeWatcherLinux]Could not bind NETLINK socket (/oneme_components/components/network_change_notifier/src/linux/network_change_watcher_linux.cpp:243)
[11-11-2026 14:41:03.680] [Fatal] [oneme-messenger]Application crashed, exception - Watcher wasn't init! (/client/oneme/src/launch/launch.cpp:102)
[6:6:20261111,144103.680322:ERROR scoped_ptrace_attach.cc:27] ptrace: Operation not permitted (1)
```
**Ключевая причина**: `Could not bind NETLINK socket` —  песочница Flatpak ограничивает доступ к NETLINK, приложение не может инициализировать сетевой монитор.
**Вывод:** проблема не в библиотеках, а в изоляции Flatpak. Нативная установка должна решить вопрос с NETLINK.

## 📜 Варианты установки

### Вариант A — AUR `max-bin` 

- Использовать 
- Переупаковка официального бинарника с `download.max.ru` под Arch.
- Мейнтейнер не вносит изменений в дистрибутив разработчика.
- Автоматически решает зависимости и интеграцию с системой.
- Минус: зависимость от AUR-хелпера и активности мейнтейнера.

**Известные проблемы (из комментариев AUR):**
- Конфликт `libsystemd` / `libpcre2` при звонках — рецепт: переименовать библиотеки, которые тащит MAX, чтобы использовались системные.
- В Sway требуется `gnome-keyring`.
- На CachyOS/GNOME — белый экран при запуске.

### Вариант B — официальный `.deb`/`.rpm` вручную

- Официальный сайт даёт только репозитории для Debian/Ubuntu и RHEL-семейства. Прямых ссылок на файлы нет.
- URL пакета можно вытащить из метаданных репозитория (`pool/main/m/max/` для deb, `linux/rpm/el/9/x86_64/` для rpm).
- Распаковать через `bsdtar` (умеет и deb, и rpm), разложить файлы, создать `.desktop`, иконки.
- Плюс: независимость от AUR. Минус: много ручной работы, хрупко при смене версии.

## 🎯 План модуля для `cup.sh`

### Что должен делать модуль

1. **Резолвер источника.** Ответить: в репах Arch нет → в AUR есть `max-bin` → предложить установку оттуда. Если AUR недоступен — вариант B.
2. **Проверка зависимостей** до установки (например, `gnome-keyring` в некоторых окружениях).
3. **Идемпотентность.** Повторный `cup install max` не должен падать с `UNIQUE` — upsert в БД или проверка «уже установлен».
4. **Запись в БД только после успеха.** Если установка упала — не писать.
5. **`remove`.** Вызывает менеджер и чистит запись в БД, чтобы БД не разъезжалась с реальностью.

### Как это вписывается в декларативность

Модуль MAX — хороший пример того, зачем нужен **резолвер источника** (см. `Cup - Декларативность`). В манифесте может быть просто `max`, а модуль сам решает: репы → AUR → официальный deb/rpm. Если источников несколько — спросить пользователя. Это ровно тот пункт «Разные источники» из раздела «Риски и сложности» заметки про декларативность.

### Порядок шагов 

- Найти источник (репы → AUR → официальный deb/rpm).
- Спросить пользователя, если источников несколько.
- Установить через выбранный менеджер.
- Проверить код возврата.
- Записать в БД (upsert).
- При ошибке — сообщение и выход без записи в БД.

## ⚠️ Риски и сложности

- **Хрупкость варианта B:** URL и имя файла меняются с версией. При смене версии модуль сломается, пока не обновишь константы.
- **Зависимость от AUR:** если мейнтейнер `max-bin` забросит пакет — модуль перестанет работать. Нужен fallback на вариант B.
- **Конфликты библиотек:** известная проблема `max-bin` с `libsystemd`/`libpcre2`. Модуль может проверять их до установки и предупреждать.
- **Запись в БД:** та же ловушка, что в `cmd_install_davinci` — `write_package` не должен вызываться при неудачной установке.
